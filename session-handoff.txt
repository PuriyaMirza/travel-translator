  The committed firebase-applet-config.json contains a Firebase web API key.
  That kind of key is public by design, so this is not a leak - noted only so

THREE JUDGEMENT CALLS, all of which deviate from a literal reading of SPEC:

  RADIUS. SPEC.md section 5 says 'Cards: 32px radius (rounded-3xl)'. Those
  disagree: rounded-3xl is 24px in Tailwind v4, confirmed against the emitted
  CSS (--radius-3xl:1.5rem). The NUMBER was honoured, not the utility name:
  rounded-card = 32px, rounded-image = 24px.

  TOKEN NAMING. :root holds the tokens under the exact names SPEC.md section 5
  gives them - that is the contract. @theme inline then maps them into
  Tailwind's utility namespaces under short semantic names:
    bg-canvas, bg-card, bg-sand, bg-charcoal
    text-brand, text-ink, text-muted, text-inverse
    border-hairline, border-blush
  This rename is forced, not preference: SPEC's --text-* colour vocabulary
  collides head-on with Tailwind v4's --text-* font-size namespace.
  --border-brand became "border-blush" deliberately, because a "border-brand"
  utility would resolve to crimson (#B91C1C) rather than SPEC's #FCA5A5 - a
  genuine footgun.

  SHADOW. shadow-soft is declared with @utility rather than as a --shadow-*
  theme token. As a token it collides with the :root name and emits a circular
  "--shadow-soft: var(--shadow-soft)" into the theme block, which only resolved
  correctly by accident of source order.

DELIBERATELY OMITTED IN M0:
  The header's hamburger and avatar slots were held open by the grid but
  rendered empty - a hamburger with no menu and an avatar with no account are
  buttons that do nothing. (Hamburger arrived in M1; avatar is still pending.)

7. THE VERCEL DEPLOY FAILURE AND ITS FIX
===============================================================================

The first preview build FAILED:

  Error: No Output Directory named "public" found after the Build completed.

ROOT CAUSE: the Vercel project was created while main held only README.md and
SPEC.md. With no package.json to detect, framework auto-detection found nothing
and fell back to the "Other" preset, which serves a static public/ directory.
Confirmed via the project API that "framework" was null.

FIX: pinned the preset in vercel.json rather than in project settings, so it
lives in version control and survives the project being recreated:

  { "$schema": "https://openapi.vercel.sh/vercel.json",
    "framework": "nextjs" }

Verified against the Vercel docs that "framework" is the documented override
and "nextjs" is a valid slug before pushing, rather than guessing.

This is exactly the class of problem M0 exists to surface - which is the point
of shipping an empty pipeline first.

NOTE FOR FUTURE SESSIONS: the sandbox cannot reach *.vercel.app directly (curl
returns 000). Verify deployments through the Vercel MCP tool's fetch instead.

8. M1 - WHAT SHIPPED
===============================================================================

Scope per SPEC.md section 10: categories, preset phrases from a local file,
editorial category pages, phrase cards, text-to-speech. No auth, no database,
no AI.

DATA LAYER
  src/lib/categories.ts - the canonical slugs, lowercase English and permanent
  per SPEC.md section 2 rule 3:
    greetings, dining, transit, shopping, lodging, emergency, general
  Display labels are localised separately in src/lib/labels.ts, so nothing is
  ever keyed off a translated string. VISIBLE_CATEGORIES drives the grid, so
  "general" cannot grow a tile by accident and /phrasebook/general returns 404
  (it is the fallback bucket for freeform translations, not a section).

  src/lib/types.ts - the Phrase interface. Every phrase carries "locale" from
  the very first write (rule 4), sourced from brand.defaultLocale rather than a
  literal.

  src/lib/phrases.ts - 42 preset phrases, exactly 7 in each of the six visible
  categories. Evenly spread, as SPEC asks (the old set was reportedly lopsided).
  House rules enforced in that file:
    - No vosotros anywhere. Formal usted with strangers.
    - Seseo throughout: c/z = "s", never "th". Written as e.g.
      "GRAH-see-ahs", never "grah-THEE-ahs".
    - ll and y as a soft "y": "YEH-vah", "TAH-yah".
    - Stressed syllable in CAPS.
    - culturalNote filled ONLY where a traveller would genuinely get it wrong.
      Most phrases have none, and that is correct - it is not padded.
  Audited programmatically: 42 total, 7 per category, unique ids, no lisped
  pronunciations, locale never hardcoded.

SCREENS
  Home: tagline, phrase of the day, 2-column category grid.
  /phrasebook/[category]: full-bleed banner, eyebrow, title, airy lead, then a
    dense scannable list. Editorial look, fast interaction - per SPEC.md
    section 5's explicit instruction NOT to build the one-card carousel.
  not-found for unknown slugs.
  Header gained the hamburger and a nav drawer now that destinations exist.

FOUR JUDGEMENT CALLS:

  PHRASE OF THE DAY is picked deterministically by UTC day number from the
  local presets - no AI, no network, no storage, and the page stays prerendered
  (revalidate 3600). The /api/daily-phrase route in SPEC.md section 6 can
  replace it later without touching the component.

  SPEECH uses useSyncExternalStore rather than effects. Voices are external
  browser state that loads asynchronously, and the distinct server snapshot
  keeps the button out of the prerendered HTML instead of mismatching on
  hydration. (The first implementation used effects and was caught by lint -
  see below.)

  THE SPEAK BUTTON IS GATED ON A VOICE EXISTING, not on the API existing.
  Devices expose speechSynthesis with an empty voice list - headless Chromium
  is one, confirmed by probe: hasSynth true, voices 0, speak() fires
  "error: synthesis-failed". On such a device a button that flashes and does
  nothing is worse than no button.
  Voice preference order: es-419, es-US, es-MX, es-CO, es-AR, then any es-*.
  European Spanish is last resort - better than silence, but it lisps, which is
  exactly what the pronunciation guides tell the reader not to do. Verified it
  picks es-MX over es-ES. Utterance rate 0.9 (slower than natural, because it
  is being repeated aloud by someone who does not speak the language).

  CATEGORY BANNERS are palette washes standing in for the photography SPEC.md
  section 5 calls for. Crimson is deliberately absent from them - it stays with
  the wordmark, primary actions and eyebrows, per "if a screen has more than two
  crimson elements, one of them is wrong". THIS IS AN OUTSTANDING PLACEHOLDER.

TWO LINT ERRORS WERE FIXED PROPERLY RATHER THAN SUPPRESSED:
  - setState called synchronously inside an effect in useSpeech - rewritten
    around useSyncExternalStore, which also fixed a hydration mismatch that
    would otherwise have shipped.
  - Same rule in NavDrawer (closing the drawer on pathname change). Rewritten
    to derive open state from the pathname it was opened on, which also handles
    the browser back button for free.

VERIFICATION PERFORMED:
  typecheck/lint/build clean. All six category pages prerender. Routes checked:
  six categories 200, "general" and unknown slugs 404. Driven in a real browser
  at 390x844: drawer opens, closes on Escape, 7 cards and 7 speak buttons per
  category, no horizontal overflow. The speech state machine was exercised
  against a STUBBED engine (because headless Chromium has no voices): idle ->
  speaking -> tap-again-stops -> auto-reset on end, one card speaking at a time,
  correct utterance text, rate 0.9, es-MX chosen over es-ES.

9. THE TAILWIND-MERGE BUG THAT SHIPPED AND WAS FIXED
===============================================================================

Found by reading the DEPLOYED HTML, not the local source. Every eyebrow label
rendered as:

  <p class="uppercase text-brand">Phrasebook: Food &amp; Drink</p>

"text-eyebrow" was MISSING - so the label silently lost its 12px size, 0.1em
tracking and 500 weight, and fell back to inherited body type.

ROOT CAUSE: the type scale lives in Tailwind's font-size namespace (text-lead,
text-h2, text-eyebrow), which overlaps the text-COLOUR namespace. Left
unconfigured, tailwind-merge read "text-eyebrow" as a colour, decided
"text-brand" superseded it, and dropped it.

The blast radius was wider than the one visible symptom. Every custom type
token paired with a colour collapsed the same way:
  text-eyebrow uppercase text-brand  ->  uppercase text-brand
  text-lead text-muted               ->  text-muted
  text-h2 text-ink                   ->  text-ink
  text-body-bold text-inverse        ->  text-inverse
Only the Eyebrow component routes through cn() today, which is why just that
one broke visibly. It would have spread through M2 and M3.

FIX: registered the scale in the font-size class group via extendTailwindMerge
in src/lib/utils.ts. One place, fixes all of it.

VERIFIED IN BOTH DIRECTIONS - this matters, because a merge that keeps
everything is as broken as one that drops everything:
  type + colour now coexist (all five cases above pass)
  genuine conflicts still collapse: text-lead text-h2 -> text-h2
                                    text-ink text-brand -> text-brand
  computed style on the rendered page back to 12px / 1.2px / 500 / uppercase
  confirmed live on the deployed preview, including the not-found page

12. "CAN I USE GOOGLE TRANSLATE INSTEAD?" - THE ANSWER
===============================================================================

No - and this is a capability fact, not a preference.

Google Translate API returns ONE string. SPEC.md section 8 requires six things
per translation:
  literal        a correct, neutral, formal-safe rendering
  natural        what a native speaker would actually say
  culturalNote   politeness conventions, false friends, local meaning shifts
  pronunciation  a guide an English speaker can read aloud and be understood
  direction      detect whether the input is English or Spanish
  category       one of the seven permanent slugs
Translate API supplies exactly one of those.

SPEC.md section 1 makes the same point as a product claim: "It is not a
general-purpose translator. Google Translate already does word-for-word; this
does what you would actually say at the counter." Building on Translate API
would leave a worse Google Translate in a nicer typeface.

IMPORTANT CLARIFICATION: the old build NEVER used Google Translate. It used
GEMINI - a generative model - which is why it could produce its "Local Nuance"
field at all. If staying in Google's ecosystem matters, Gemini is the real
alternative and would change exactly one file (src/lib/translate.ts) plus the
dependency; the rest of the M2 plan is provider-independent.

The user chose ANTHROPIC, per SPEC.md section 3.

13. M2 PLAN AS APPROVED
===============================================================================

Scope per SPEC.md section 10 was: /translate, the route handler, the result
card, all three states - with no auth until M3.

THE USER CHANGED THIS. They chose to gate the route behind auth so it is never
a public endpoint. That reshapes the milestone; see the consequences below.

WHAT GATING ACTUALLY COSTS (this was raised before any code):
  Client-side gating is NOT protection. Hiding the form behind a login check
  still leaves /api/translate callable with curl. Real protection means the
  route verifies a Firebase ID token server-side on every request, which pulls
  in Firebase Auth (M3 work, now in M2), firebase-admin, and a service-account
  secret in addition to the public web config.

A PRODUCT CONCERN WAS RAISED ONCE AND THE USER'S DECISION STANDS:
  SPEC.md section 7 designs for logged-out use - "Logged out: phrases go to
  localStorage... on login, upload local phrases" - which assumes the app is
  useful before you have an account. A login wall on the core feature cuts
  against that, and account creation is a poor first experience for someone at
  a counter on bad signal. If cost is the real worry, an input cap plus a
  coarse per-IP throttle addresses it far more cheaply. Recorded, not
  re-litigated.

BUILD ORDER:

  1. AUTH FOUNDATION
     src/lib/firebase.ts        client init, Auth only (Firestore is M3; when
                                it lands use persistentLocalCache via
                                initializeFirestore - enableIndexedDbPersistence
                                is deprecated, per SPEC.md section 7)
     src/lib/firebaseAdmin.ts   server-only Admin init for token verification
     src/components/AuthProvider.tsx   context exposing user + loading
     src/app/(auth)/sign-in/page.tsx   email/password sign in and sign up
     Header's right slot finally gets its avatar - the placeholder held open
     since M0.

  2. SERVER: src/lib/translate.ts
     Owns the prompt, schema, call and normalisation. Never imported by a
     client component - the key stays server-side (rule 6).
     - SPEC.md section 8's template with {{LOCALE_NAME}} as a PARAMETER, never
       a literal (rule 2).
     - Few-shot examples neutral Latin American: "Me da el menu?",
       "Donde tomo el autobus?" - never the old build's guagua/bregando.
     - User text goes in a USER message, never interpolated into the system
       prompt.
     - Structured outputs via client.messages.parse() + zodOutputFormat() in
       output_config.format. This REPLACES SPEC.md section 8's "output strictly
       valid JSON, no markdown fences" instruction, which is a request the
       model can simply fail. parsed_output is nullable - guard it.
     - NORMALISE BEFORE RETURNING: validate the returned category with the
       existing isCategory() from src/lib/categories.ts, falling back to
       "general". This is precisely the bug class rule 3 exists to prevent.
       Attach locale from brand.defaultLocale so results are savable in M3 with
       no migration (rule 4).

  3. ROUTE: src/app/api/translate/route.ts
     POST. Verifies the Firebase ID token BEFORE doing any work - no token, no
     model call, no spend.
     - Reject empty input; cap length at 500 chars (a phrase, not a document).
     - Typed error chain, most specific first: AuthenticationError,
       RateLimitError, APIError - mapped to codes the client turns into copy.
     - NEVER echo the provider's name or raw message to the client (SPEC.md
       section 6). Log server-side.

  4. SCREEN: /translate
     The result card is the EXISTING PhraseCard. The API returns a
     Phrase-compatible object, so results render through the M1 component,
     text-to-speech included. No parallel card implementation.
     One change makes that work: translation is bidirectional, so an es->en
     result is English while PhraseCard hardcodes lang="es" and useSpeech

14. TWO SPEC CONFLICTS WITH THE CURRENT ANTHROPIC API
===============================================================================

Both were verified against current API documentation, not recalled from memory.

(1) "temperature" IS REJECTED.
    SPEC.md section 8 says "Set temperature around 0.3." Sampling parameters
    (temperature / top_p / top_k) are REMOVED on claude-opus-5 and return a 400.
    The request would fail outright.
    Instead: structured outputs plus a tight prompt, with
    output_config: { effort: "low" } - appropriate for a short, well-specified
    transformation task.

(2) max_tokens: 1024 RISKS TRUNCATION.
    Reasonable arithmetic for a few-hundred-token JSON response, but THINKING
    TOKENS COUNT TOWARD max_tokens, and thinking is on by default on
    claude-opus-5. Use 2048 for headroom.
    Disabling thinking is the other lever but has known failure modes on
    Opus 5 - it can write a tool call into visible text, and can leak tags - so
    lowering effort is the better control.

MODEL: claude-opus-5. SPEC.md section 3 says to check the docs for the current
model string rather than assume one. Do not append date suffixes to model IDs.
